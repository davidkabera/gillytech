## Status
Accepted for MVP — 2026-08-20

## Scope

This ADR covers the **MVP architecture only**. Supabase Cloud is used here
for both Auth and Postgres persistence because it is the fastest path to a
working, deployed product. This is a deliberate short-term choice, not a
long-term commitment to Supabase as the system of record — see
[Future Direction](#future-direction-post-mvp) below. Any future migration
of the persistence layer will be captured in a superseding ADR (e.g.
ADR-0002) rather than by editing this one.

## Context

Gillytech is a monorepo application consisting of a React/Vite frontend and a
Node.js/Express backend, originally developed against a local Supabase
instance. The project needed to move from local development to a live,
publicly reachable deployment with:

- A managed Postgres database with built-in authentication (email/password,
  row-level security).
- A backend API that can validate Supabase-issued JWTs and serve business
  logic independently of the frontend.
- A frontend that is cheap to host, deploys on every push, and can be handed
  a stable API base URL.
- A single Git repository housing both frontend and backend without leaking
  secrets, `node_modules`, or local Supabase CLI artifacts into version
  control.

The team (single maintainer: Dave / cto-kabera) needed this to work
end-to-end for a live demo/production environment, not just local dev.

## Decision

Adopt the following architecture:

```
[ React / Vite Frontend ] (Vercel)
        │
        ├──► Supabase Cloud (Auth & PostgreSQL Database)
        │
        └──► [ Node.js / Express API ] (Render) ──► Supabase Cloud
```

**1. Supabase Cloud for Auth + Database**
Rather than self-hosting Postgres and rolling custom auth, Supabase Cloud
provides `auth.users`, GoTrue-based session/JWT issuance, and Postgres with
Row Level Security (RLS) out of the box. A `handle_new_user` trigger
propagates every new `auth.users` row into `public.users`, keeping the
application's user table in sync with the auth layer without application
code.

**2. Express API on Render, decoupled from the frontend**
Business logic and any privileged operations live in a dedicated Express
service rather than in frontend-callable Supabase functions. The backend
validates requests using the same JWT secret as the Supabase project, so a
session issued by Supabase Auth is independently verifiable by the API
without a round trip to Supabase for every request.

**3. React/Vite frontend on Vercel, backend URL injected via env var**
The frontend is a static Vite build deployed from the `frontend/` directory
of the monorepo. It talks to Supabase directly for auth state and to the
Render-hosted API (via `VITE_API_URL`) for application data.

**4. Monorepo with isolated environment/dependency boundaries**
`frontend/` and `backend/` each carry their own `.gitignore` (for `.env`,
`node_modules/`), with a root-level `.gitignore` covering `.supabase/` and
root `node_modules/`. Each service is deployed from its respective
subdirectory (Vercel Root Directory = `frontend/`, Render root = `backend/`).

## Consequences

**Positive**
- No self-managed auth or database infrastructure — Supabase handles
  password hashing, token issuance, and RLS enforcement.
- Frontend and backend deploy and scale independently; a backend outage on
  Render doesn't take down the static frontend on Vercel.
- JWT verification on the backend is stateless once the Supabase JWT secret
  is synced — no session store needed in Express.
- Monorepo keeps frontend/backend co-located for a single-maintainer
  workflow while still deploying as two independent services.

**Trade-offs / things to revisit**
- Render's free/low tiers cold-start after inactivity, which will show up as
  first-request latency in the live demo. Worth monitoring if this becomes
  user-facing.
- The backend and Supabase share a JWT secret; if that secret rotates in
  Supabase, the Render env var must be updated in lockstep or auth will
  break silently with `Invalid or expired token`. This is a manual step
  today (see runbook) and is the most likely source of future auth
  incidents.
- RLS policies were added narrowly (authenticated `SELECT` on
  `public.users`) to unblock the immediate error. As more tables and write
  paths are added, policies should be reviewed as a set rather than
  patched one error at a time.
- CORS origins (`localhost:5173`, `localhost:4173`, the Vercel domain) are
  hardcoded in Express middleware. Adding a new environment (e.g. a
  staging Vercel URL) requires a backend code change and redeploy, not just
  a config change.

## Alternatives Considered

- **Self-hosted Postgres + custom auth**: rejected — more operational
  surface area for a single maintainer, no material benefit over Supabase's
  managed auth for this project's scale.
- **Serverless functions (Vercel Functions / Supabase Edge Functions) instead
  of a standalone Express service**: not adopted for this iteration; a
  standalone Express API was already in progress and keeps backend logic in
  one place rather than split across platforms. Worth revisiting if Render
  cold-starts become a real problem.
- **Netlify instead of Vercel**: not evaluated in depth; Vercel was chosen
  primarily for GitHub integration convenience.

## Future Direction (Post-MVP)

Supabase's hosted Postgres is treated as an **interim persistence layer**,
not a permanent one. As the application outgrows what's practical on
Supabase's database (schema complexity, query patterns, cost at scale, or
just wanting full operational control), the plan is to:

- **Migrate persistence to a standalone Postgres instance** that the
  Express backend owns and connects to directly, decoupled from Supabase's
  hosted database.
- **Retain Supabase strictly for Auth.** The backend already validates
  Supabase-issued JWTs independently via the shared JWT secret (see
  Decision §2), so this split is architecturally cheap — the backend
  doesn't need to change how it authenticates requests, only where it reads
  and writes application data.
- Carry over the `public.users` sync pattern conceptually: the standalone
  Postgres will need its own mechanism to stay consistent with
  `auth.users` (e.g. the backend upserts a local user record on first
  authenticated request, replacing the `handle_new_user` trigger which only
  works within Supabase's own Postgres instance).

This means the RLS policies and grants documented in this ADR (§3.3 of the
runbook) are expected to become obsolete for anything except the
`auth`-related tables once the migration happens — they should not be
extended indefinitely as the schema grows. That growth is itself a signal
to trigger the migration rather than adding more Supabase-side policies.

**This ADR should be marked Superseded (in part) once that migration ADR is
written and merged.**
